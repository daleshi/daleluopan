## Context

**现状数据链路**（请求驱动）：浏览器 → `server.js` → `smartCacheGet`（内存 → 磁盘 JSON → 过期则同步调外部源）。命中缓存时毫秒级返回，缓存过期时请求线程等待外部源（实测 2.7～7 秒），外部源限流时直接影响页面。

**现状存储**：`data/*-watchlist.json`（关注清单，4 类共 36 项：指数 14、股票 5、ETF 5、基金 12）+ `data/cache/*.json`（最新数据快照，覆盖写）。`indices.json` 4.9MB、`active-funds.json` 4MB，大头是 10 年 K 线与净值序列。

**生产环境**（不更换）：CentOS 7.6、glibc 2.17、gcc 4.8.5、Node 16.20（nvm）、内存 2GB。部署方式为本地打包 → 上传覆盖 → PM2 重启，打包内容不含 `node_modules`，服务器上沿用已有依赖目录。

**SQLite 驱动实测**（2026-09-30，在生产机 `/tmp` 隔离目录）：

| 驱动 | 结果 | 说明 |
|---|---|---|
| better-sqlite3@9 | 安装失败 | 无匹配预编译包，源码编译需要更新的 C++ 工具链，gcc 4.8.5 不满足 |
| Node 22 内置 `node:sqlite` | 不可用 | 需要升级 Node，而 Node 18+ 官方二进制要求 glibc 2.28+ |
| **sql.js@1**（SQLite 编译为 WASM） | 可用 | 无原生依赖；写 10.4 万行并落盘 299ms，区间查询 25ms，库文件 4.0MB，进程 RSS 71MB |

**已验证的数据源**（2026-09-30）：

| 数据 | 数据源 | 覆盖 | 粒度 |
|---|---|---|---|
| 指数 PE/PB 历史 | 蛋卷 `djapi/index_eva/pe_history`、`pb_history` | 9/12 个关注指数，多数 2016-09 起 | 周线（末点为当日） |
| 分位参考线 | 蛋卷同一接口 `horizontal_lines` | 同上 | 30/50/70 分位值 |
| 港股创新药 PE | 中证官网 `csindex-home/perf/index-perf`（字段 `peg`） | 2021-10-18 起 | 日线，无 PB |
| 股票 PE/PB 历史 | 东财数据中心 `RPT_VALUEANALYSIS_DET`（`PE_TTM`、`PB_MRQ`） | 5/5 只，2018-01-02 起 | 日线，仅 A 股 |
| 创业板50、自由现金流 K 线 | 国证官网 `getIndexDailyDataWithDataFormat` | 2010-05 / 2012-12 起 | 日线，含开盘价、成交量 |
| K 线开盘价 / 成交量 | 东财 push2his（现有解析已取到，组装时被丢弃） | 全部 | 日线 |
| 温度 | 有知有行详情接口 | 仅当前值 | 无历史 |

口径验证：沪深300 中证官网 `peg`=13.09，蛋卷 PE=13.13，同为滚动 PE。

**关键约束**：稳定优先；服务器系统与 Node 版本不变；外部源会限流；中证数字指数（如 931787）仅东财 `2.xxx` 可用；部署规则为不覆盖 `data/`。

## Goals / Non-Goals

**Goals:**
- 网站任何请求都不同步调用外部源，页面在外部源故障时照常显示上一份数据并标注时间
- 建立永久的估值快照、日 K、净值、温度历史
- 上线首日即可展示多年估值曲线（通过历史回补）
- 任一进程崩溃不影响另一进程；采集可重跑且幂等
- 不改动服务器系统、Node 版本与部署流程的主体

**Non-Goals:**
- 不存盘中 tick 或分钟线（只保留最新值 + 每日快照）
- 不为创业板50、自由现金流、163415 LOF 寻找付费估值源
- 不做百分位曲线（只画 PE/PB 数值曲线 + 分位参考线）
- 不做港股 / 美股个股估值（当前关注的股票均为 A 股）
- 不在本变更中删除旧的请求时采集逻辑与 JSON 缓存（留给 `retire-json-cache`）
- 不把关注清单迁入数据库（见 D3）

## Decisions

### D1：驱动选 sql.js

**理由**：生产机上唯一实测可用的 SQLite 方案；纯 JS + WASM，Mac 与服务器上的包文件完全相同，不需要在服务器上编译；性能满足本项目量级。
**代价**：库整体加载在进程内存中，写入后需要自己导出到文件；多个进程不能共享同一个活动库。D2 围绕这一点设计。
**放弃的备选**：better-sqlite3（服务器上无法安装）；升级到 Node 22 非官方 glibc 2.17 构建以使用 `node:sqlite`（实验性模块 + 非官方构建，不符合"稳"）。

### D2：热数据与历史数据分离，单写多读，原子落盘

```
                 ┌───────────────────────────────┐
                 │ dale-collector（唯一写入者）      │
                 │ 内存中持有 sql.js 库              │
                 └──────┬─────────────────┬──────┘
      每轮采集后          │                 │  每个任务完成后（收盘快照、
      写临时文件再改名     ▼                 ▼  回补、缺口补齐），写临时文件再改名
         ┌──────────────────────┐   ┌──────────────────────────┐
         │ data/db/latest.json   │   │ data/db/market.db          │
         │ 最新行情 + 采集状态     │   │ 日K / 净值 / 估值 / 温度 / 分位 │
         │ 几十 KB，盘中 5～10 秒一写 │   │ 一天几次                     │
         └──────────┬───────────┘   └─────────────┬────────────┘
                    │ mtime 变化才重读              │ mtime 变化才重新加载
                    ▼                              ▼
         ┌────────────────────────────────────────────────┐
         │ dale-compass（网站，只读）                         │
         │ 内存中持有 latest 对象 + 一份只读 sql.js 库副本         │
         └────────────────────────────────────────────────┘
```

- **重量快照**（实现时补充）：`/api/indices`、`/api/active-funds` 的响应含 10 年 K 线与净值序列（4～7MB），由现有 `fetchAllIndexData` / `fetchAllActiveFundData` 组装。为保持接口输出完全不变，采集进程把这两份结果原样写入 `data/db/snap/{indices,active-funds}.json`（交易时段 5 / 15 分钟一次，休市 60 / 180 分钟），网站 db 模式直接返回。`retire-json-cache` 时再改为从库组装
- **原子写入**：所有文件都先写到同目录的 `*.tmp`，`fsync` 后 `rename` 覆盖。`rename` 在同一文件系统内是原子的，网站永远读到完整的旧文件或完整的新文件，不会读到写了一半的内容
- **网站感知变化**：请求到来时检查文件 mtime（结果缓存 1 秒，避免每个请求都 `stat`）；变化才重读。`latest.json` 解析成本可忽略；`market.db` 重新加载发生在收盘后等少数时点，加载完成后才替换旧副本，加载失败则继续用旧副本
- **崩溃影响**：采集进程在两次落盘之间崩溃，只丢失正在进行的那个任务的结果；由于写入幂等（D4），重启后重跑即可
- **启动恢复**：采集进程启动时加载 `market.db`；文件损坏时自动改用最新一份备份，并记录告警
- **采集状态**：每类的最近成功时间、连续失败次数、当前间隔写在 `latest.json` 里，不写库，避免库每几秒就变一次

**放弃的备选**：
- 把最新行情也放进库、每轮导出整个库：库文件预计十几 MB，每 5～10 秒导出一次既浪费 IO，也会让网站频繁重新加载
- 网站通过内部接口向采集进程查询历史：多一条进程间通信链路，采集进程挂掉时历史曲线也不可用，与"互相隔离"冲突

### D3：关注清单留在现有 watchlist 文件，库中只保留镜像

关注清单的增、删、排序仍由网站写现有的 `data/*-watchlist.json`，接口与逻辑不变。库中的 `instruments` 表是**采集进程维护的镜像**：

- 采集进程每轮检查 watchlist 文件 mtime，变化时同步到 `instruments`：新出现的标的插入（`status=active`），从文件中消失的标记 `status=deleted` 并记下 `deleted_at`
- 历史表以 `instruments.id` 关联，`instruments` 以（类型、代码、市场）唯一，所以**删除后历史自动保留，重新添加同一标的时匹配回原记录，历史自动接续**——不需要在 watchlist 文件里加软删除标记，旧代码读取 watchlist 的地方都不用改
- 页面上显示哪些标的、按什么顺序，始终以 watchlist 文件为准；库只提供数据

**理由**：库只有采集进程一个写入者，彻底避免多进程写同一个库；关注清单几十行，放进库没有实际收益。

### D4：表结构

```
instruments          关注清单镜像（采集进程维护）
  id PK │ type(index/stock/etf/fund) │ code │ market │ secid │ name
  │ dj_code │ cs_code │ tracking_instrument_id（ETF → 跟踪指数）
  │ valuation_source（danjuan/csindex/eastmoney_dc/none）
  │ status(active/deleted/hidden) │ created_at │ deleted_at │ extra JSON
  UNIQUE(type, code, market)

kline_daily          日 K（可回补）
  PK(instrument_id, trade_date) │ open │ high │ low │ close │ volume │ amount
  │ change_pct │ change_amt │ source

fund_nav_daily       基金净值（可回补）
  PK(instrument_id, nav_date) │ nav │ acc_nav │ daily_return │ source

valuation_daily      估值快照（永久保存）
  PK(instrument_id, trade_date) │ pe │ pb │ pe_pct │ pb_pct │ roe │ dividend
  │ eva_type │ temperature │ source │ granularity(daily/weekly)
  │ is_fallback（收盘抓取失败、用盘中值兜底）│ fetched_at

valuation_bands      分位参考线（按标的、指标，随最新一次回补更新）
  PK(instrument_id, metric(pe/pb)) │ p30 │ p50 │ p70 │ source │ updated_at

collector_runs       每日任务日志（收盘快照、基金净值、回补、缺口补齐、备份）
  id │ job │ market │ started_at │ finished_at │ status │ ok_count │ fail_count │ error

schema_version       结构版本（迁移用）
```

`latest.json` 结构：

```
{ updatedAt, quotes: { "index:000300.SH": { price, changePct, …, pe, pb, temperature,
                                            source, fetchedAt, tradeDate }, … },
  status:  { index: { lastOkAt, failCount, intervalMs }, stock: …, etf: … } }
```

**要点**：
- **主键即幂等**：同一标的同一天重复写入为覆盖，任何任务都可以安全重跑
- **最新行情以（类型:代码.市场）为键**：新添加的标的不必等库里分配 id，下一轮采集就能出现在 `latest.json` 里
- **通用字段拆列，其余放 JSON**：四类标的字段差异大（基金 40+ 个字段）
- **ETF 不重复存估值**：通过 `tracking_instrument_id` 指向跟踪指数；跟踪指数不在关注清单时，以 `status=hidden` 的内部标的存在，参与估值采集但不在页面显示
- **温度与 PE/PB 同表**：同一交易日的一行快照，查询和对齐都简单

体量实测（2026-09-30，36 个标的完成回补）：日 K 7.3 万行、净值 2.5 万行、估值 1.7 万行，库文件 9.6MB；加载 17ms、导出 30ms、10 年区间查询 29ms。采集进程稳定后 RSS 约 270MB（heap 30MB，主要为 fetcher 内部缓存与 WASM 堆），PM2 上限设 600MB。

### D5：盘中采集节奏

```
每类（指数 / 股票 / ETF）一个独立计时器：
  下次间隔 = random(5s, 10s)
  失败      → 退避：10s → 20s → 40s → 80s → 120s（上限）
  成功      → 回到 random(5s, 10s)
  连续 N 次数据未变 → 间隔 × 2（上限 60s），数据变化即恢复
  午休 / 休市 → 停止，按下一个开盘时间唤醒
```

**理由**：随机区间 5～10 秒平均 7.5 秒，每类每小时约 480 次请求，仅比固定 10 秒多约三成；下限 5 秒避免连续突发请求。三类独立计时，请求在时间轴上分散。请求头沿用现有浏览器 UA 与 Referer，不轮换 UA。

**休市时新增标的**：采集进程在休市时仍每 30 秒检查一次 watchlist；发现新标的时立即单独抓一次最新行情写入 `latest.json`，并排队回补其日 K。

### D6：交易时段与交易日

- **统一实现**：将 `stockFetcher.js`、`etfFetcher.js`、前端 `isMarketOpen` 三处交易时段判断合并为一个共享模块（后端），前端改为读取接口返回的市场状态
- **时段**（北京时间）：A 股 09:30–11:30、13:00–15:00；港股 09:30–12:00、13:00–16:00；美股 21:30–次日 04:00（夏令时）/ 22:30–次日 05:00（冬令时），按美东时区规则自动切换
- **节假日**：不维护节假日表。收盘后拉取最新一根日 K，若日期与库中最后一根相同，则判定当天休市，跳过快照
- **交易日归属**：按交易所当地日期；美股北京时间周二凌晨收盘记为美东周一

### D7：收盘快照与兜底

实测发现各源公布时间不同（2026-09-30）：日 K 收盘即出；东财个股估值当天即出；蛋卷指数估值与知有行温度在**晚间**才更新到当日（15:05 时仍是前一交易日）。因此拆成两类任务：

```
日 K    收盘 +5 分钟起，每 5 分钟重试（只处理还没拿到当日 K 线的标的），最长 2 小时
        连续 3 次没有任何标的出现当日 K 线 → 判定休市
估值    北京时间 09:00 / 16:30 / 19:30 / 21:30 / 23:00 各执行一次（每天，含周末）
温度    按数据源自身公布的日期写入，重复执行幂等；23:00 那次对当日仍缺失的
        A 股交易日标的写入盘中最后一次成功值（PE/PB 与温度分别标记兜底）
        次日 09:00 若数据源补发了当日值，正常值覆盖兜底值
每个任务完成后导出 market.db（原子落盘）
```

日 K 数据源按顺序尝试：全量回补时国证 / 中证官网（2000 年起完整历史）→ 东财（单次最多约 2000 条）→ 腾讯分段（个股 / ETF）→ 现有 failover 链；增量时东财优先。兜底源的 0 占位成交量 / 成交额置空，涨跌幅按前收盘价补算。

**理由**：K 线和净值事后可以补；温度与当日估值只能当天取，所以需要多次重试和兜底。

### D8：历史回补与单曲线单数据源

每个标的在 `instruments.valuation_source` 上固定一个主数据源，同一条曲线只取这一个源的数据，避免切换源时曲线跳变：

| 标的 | 主源 | PE | PB | 粒度 |
|---|---|---|---|---|
| 蛋卷覆盖的 11 个指数（含全指信息、标普500、纳指100，实测补充） | danjuan | ✓ | ✓ | 历史周线，上线后每日 |
| 港股创新药 931787 | csindex | ✓ | ✗ | 日线 |
| 5 只 A 股 | eastmoney_dc | ✓ | ✓ | 日线 |
| 4 只 ETF | 跟随跟踪指数 | — | — | — |
| 创业板50、自由现金流、163415 | none | — | — | 显示"暂无估值数据" |

回补为采集进程内的任务，按标的串行、请求间加随机间隔；每完成一个标的导出一次库，中断后可重跑（主键幂等）。

### D9：估值曲线横轴按日期

历史为周线、上线后为日线，按点序号排横轴会把近期拉宽、历史挤压。估值曲线横轴按真实日期比例绘制；周期按钮（1/3/5/10 年）按日期截取。现有价格走势图的交互（点击锚点看详情）保持一致。

### D10：迁移与切换开关

```
阶段 1  部署采集进程 + 建库 + 一次性导入与回补
        网站继续走原有逻辑（双跑），对比库中数据与原接口输出
阶段 2  开关 dataSourceMode=db：网站接口改为读 latest.json + market.db
        原逻辑保留，可一键切回 legacy
阶段 3  估值 / 温度曲线上线（仅依赖库，不受开关影响）
阶段 4  稳定 1～2 周后，另起变更 retire-json-cache 删除旧逻辑
```

开关放在 `data/site-config.json`（已有站点配置文件），管理端可切换，无需重新发布。

### D11：部署与依赖

- 新增依赖 `sql.js@1`，写入 `package.json` / `package-lock.json`
- `scripts/package-deploy.sh` 把 `node_modules/sql.js` 一起打进发布包（纯 JS，与平台无关），服务器上**不执行** `npm install`
- `ecosystem.config.js` 新增 `dale-collector` 应用；首次部署后 `pm2 start ecosystem.config.js --only dale-collector` 并 `pm2 save`
- 同步更新 `deploy-to-server` 技能中"不执行 npm install、新增依赖需手动处理"的说明

### D12：备份

采集进程每日最后一个收盘任务完成并落盘后，把 `market.db` 复制为 `data/backup/market-YYYYMMDD.db`，保留最近 14 份。因为 `market.db` 始终是原子写入的完整文件，直接复制即可得到一致的备份。库文件位于 `data/` 下，现有"部署前备份 `data/`"流程会一并带上。

## Risks / Trade-offs

- [外部源持续限流] → 网站只读本地文件，显示上一份数据并标注"X 分钟前"；采集退避到 2 分钟上限，不放大请求
- [采集进程崩溃] → PM2 自动重启；网站继续读最后一次落盘的文件，数据时间戳显示滞后
- [写到一半断电或崩溃] → 临时文件 + `rename` 原子替换，磁盘上始终是完整文件；最多丢失进行中的那个任务，重跑幂等
- [网站重新加载 market.db 时阻塞事件循环] → sql.js 加载为同步操作，预计百毫秒级；只在 mtime 变化时发生（每天几次、多在收盘后），上线前实测；若超过 500ms，改为在 worker 线程中加载后再切换
- [两份内存副本占用内存] → 每个进程约增加库文件 2 倍的内存，预计合计 100MB 以内（服务器 2GB）；上线前实测
- [库文件增长] → 按估算十年内保持在几十 MB；超过阈值时再评估按年分库
- [历史回补数据与实时口径不一致] → 每行记录 `source`，同一曲线只用一个源
- [估值快照某日缺失] → 有盘中值兜底；兜底行标记 `is_fallback`，曲线上可区分
- [迁移期间两套数据不一致] → 阶段 1 双跑对比，确认一致再切换
- [库文件损坏] → 启动时自动改用最新备份；每日备份保留 14 份；原 JSON 缓存在 `retire-json-cache` 之前一直保留

## Migration Plan

1. 本地实测：用真实数据导入后的库文件大小、导出耗时、网站加载耗时与内存
2. 部署：新代码（含 `node_modules/sql.js`）→ 采集进程首次启动建库 → 从 watchlist 与 JSON 缓存导入 → 执行历史回补
3. PM2 新增 `dale-collector` 应用，`pm2 save`
4. 双跑观察 1～3 个交易日，对比库与原接口数据
